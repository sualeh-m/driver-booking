# ShiftControl

Internal HGV/Warehouse shift-booking app for a recruitment agency — a spreadsheet-style editable grid (workers × dates) that replaces the team's Google Sheets workflow. Bookings are organised per **sheet** (a client depot + worker type).

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server (port 5000)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- Required env: `DATABASE_URL` — Postgres connection string

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5
- DB: PostgreSQL + Drizzle ORM
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)

## Where things live

- DB schema (source of truth): `lib/db/src/schema/*.ts` — mirrors the user-provided v2 `attached_assets/extracted_files/schema.sql` exactly. Active tables: users, sheets, sheetContacts, workers, workerSheets, bookings, auditLog, messages, events, leavers, submissions. shiftRequirements is read-only (exposed for linking submissions; the roster itself is not managed in-app). `session` is infra (provisioned via Drizzle, see Gotchas).
- API contract (source of truth): `lib/api-spec/openapi.yaml` — drives codegen (React Query hooks + Zod schemas in `@workspace/api-client-react`).
- Backend routes: `artifacts/api-server/src/routes/*.ts`; helpers in `artifacts/api-server/src/lib/` (serialize, auth, session, csv, dates); wiring in `src/app.ts`.
- Frontend: `artifacts/driver-grid/src/` — grid in `components/grid/BookingGrid.tsx`, layout in `components/layout/Shell.tsx`.
- Rest-day rule (shared): `lib/rest-rules/src/index.ts` — single source of truth for thresholds (`REST_DAY_RULES`), the set of job roles the rule applies to (`REST_RULE_JOB_ROLES` = `["HGV 1","HGV 2","Trunker"]`, gated via `isRestRuleJobRole`), and the consecutive-working-day logic used by both the server (enforcement in `bookings.ts`, counters in `grid.ts`) and the frontend. The rule keys off a worker's **job role**, NOT the sheet type — so it applies to those 3 roles even on a "Both" sheet and never to the other roles.

## Architecture decisions

- Contract-first: OpenAPI spec generates client hooks and Zod validators; serialize.ts converts `Date → ISO string` because generated Zod expects strings (DB date cols use Drizzle `mode: "string"`).
- Auth is email + password with two roles (`admin`/`standard`). Passwords are hashed with Node's built-in scrypt (`lib/password.ts`, format `scrypt$salt$hash`, no external dep). Session cookie via `express-session` + `connect-pg-simple`; same-origin, so cookies auto-send. Mutations read `req.session.userId` for the audit trail. There are NO email/invite flows — an admin sets a temporary password and the user is forced to change it on first login / after a reset (`users.must_change_password`). **Authorization is enforced server-side, never UI-only:** admin-only routes attach `requireAdmin` (from `lib/auth.ts`) PER-ROUTE — never `router.use(requireAdmin)`, which leaks the gate onto every router registered after it (this caused a real bug blocking standard users from `/sheets`). `getCurrentUser`/`enforcePasswordChange` also live in `lib/auth.ts`. Admin-only capabilities: user management (`routes/users.ts` CRUD + reset-password, with self-delete and last-admin-demote guards), delete a whole sheet, and delete a leaver record. Everything else is allowed for any logged-in user.
- A "working shift" = a booking with `startTime` set; per-day totals count these.
- Client-email and send-confirmation endpoints compute real previews server-side; actual sending (Vincere / MS Graph / Twilio) is deferred to Phase 2 stubs.

## Product

Spreadsheet-style grid (workers down, dates across) scoped to the selected **sheet**, with Day/Week/Month toggle (Week = Sun–Sat, Month from 1st), inline status + 24h start-time editing, colour-coded status cells. **Grid scrolling/layout:** the grid uses ONE scroll container — a raw `<table>` inside a single `flex-1 min-h-0 overflow-auto` div (NOT the shadcn `Table`, whose own nested `overflow-auto` wrapper put the horizontal scrollbar below all rows where it was unreachable, cutting Month view off ~mid-month). **`min-h-0` is REQUIRED on every flex child in the height chain** (`Shell` is `h-screen flex-col`; `Grid.tsx`'s `flex-1 min-h-0 overflow-hidden` wrapper; `BookingGrid`'s `flex-1 min-h-0 overflow-auto`) — without it a flex item's default `min-height:auto` makes the scroll div balloon to full content height so `<main>` becomes the scroll container and the horizontal scrollbar sits below all rows (you'd have to scroll all the way down to reach it). With `min-h-0` the inner div is viewport-bounded so the horizontal scrollbar is reachable at the bottom of the visible grid and you can scroll dates left/right without scrolling down first. The header row is `sticky top-0` and the left **Worker** name column is `sticky left-0` (header cell z-20, body name cells already opaque via role fill / bg-background) so it stays frozen while dates scroll. Table width is `w-full` in Week/Month (Month overflows → horizontal scroll reaches every day) but `w-auto` in **Day view** (`isDayView = days.length === 1`) so the lone date column stays compact instead of stretching across the screen. **Past/today shading:** comparing each column's `yyyy-MM-dd` to today — past dates are dimmed (header muted bg + muted text; body cells get a slight `opacity-70` over a `bg-muted/50` td — this intentionally fades past *bookings* too so the whole past column reads as historical; the colour palette itself is unchanged and today/future cells render at full strength) and **today** is highlighted (header `bg-primary/10` + primary ring + "· Today" label; body td faint `bg-primary/5`); future days render normally. Display-only, status colours unchanged. The grid also has a per-worker standing note column (from `workerSheets.notes`), and per-day working-shift totals. Two independent colour systems (defined in `BookingGrid.tsx` / `index.css`): (1) **status cell colours** — muted, dark-text-on-light: Available=soft yellow, Pre-Booked=soft orange, Confirmed=green, Rest=white, Off=soft grey, Holiday=black with a white ✕, No Show=red; the bottom legend mirrors these. (2) **worker-name CELL background shading by job role** (`ROLE_CELL_BG`, applied to the sticky left name `TableCell`): HGV 1=green, HGV 2=teal, Trunker=light purple, Van=soft blue, Forklift=muted amber, Drivers Mate=soft grey-blue, Warehouse=soft brown/tan, Other=grey (null/unknown role → default `bg-background`). The fills are soft/PALE so the normal dark name text stays readable; the name text itself is NOT colour-shaded. Top actions (the toolbar is **icon-only** — `GridToolbar.tsx` renders each as a `size="icon"` Button in a `flex-nowrap` row with a Radix tooltip showing its name on hover + an `aria-label`; disabled buttons don't fire tooltips, which is fine): Add Worker (pick a fixed job role; worker type is derived, see Job roles + worker type), New Sheet (client company, depot, worker type HGV/Warehouse/Both — **NO sheet-name field**; the sheet `name` is auto-derived as `Client — Depot` via `sheetDisplayName` in `serialize.ts`, used on BOTH insert and in `serializeSheet` so existing sheets and any future client/depot change always display in that format; the selector shows `name · workerType`), Sheet Settings (manage multiple client contacts, one primary), Export CSV (client-side), Email-to-client preview (uses the sheet's primary contact), Send-confirmations preview. The **Import CSV** toolbar button was removed (the `ImportCsvDialog` component and the server CSV-import endpoint in `grid.ts` are intentionally kept in code, just no longer surfaced in the UI). Email/password login with two roles, forced password change on first login / after reset, full audit trail, Activity view.

**Job roles + worker type (built):** a worker's job role is a fixed set of 8 — HGV 1, HGV 2, Trunker, Van, Forklift, Drivers Mate, Warehouse, Other — defined in ONE place: the `JobRole` enum in the OpenAPI spec (codegen emits a `JobRole` const the frontend dropdowns build from via `Object.values`). It is a Select everywhere a worker's role is set/edited (`AddWorkerDialog`, `WorkerProfileDialog`). A worker's `worker_type` (still only HGV or Warehouse, CHECK unchanged) is **DERIVED server-side from the job role** (`workerTypeForJobRole` in `routes/workers.ts`: an HGV-type role → HGV, else Warehouse) on both POST and PATCH — it is NO LONGER user-editable and the dialogs have no worker-type field. Sheets, by contrast, can be **HGV / Warehouse / Both** (`SheetWorkerType` enum; `sheets_worker_type` CHECK widened to include `Both`); a Both sheet accepts workers of any role. CSV import on a Both sheet derives each new worker's type from its row's job role (`grid.ts`).

**HGV rest-day safety check (built):** for workers in an HGV-type job role only (HGV 1, HGV 2, Trunker — `isRestRuleJobRole`, NOT the sheet type), the grid shows a per-day counter (white pill, top-right of each cell) of consecutive working days (Confirmed/Pre-Booked count; Rest/Off/Holiday reset). When booking such a worker into a working status: at the warn threshold (6) it warns but allows with a confirmation dialog ("Book anyway"); at the block threshold (7) it is blocked server-side (cannot save). Workers in any other role have no limit and no counter — even on a Both sheet. Thresholds live in ONE place: `REST_DAY_RULES` in `@workspace/rest-rules` (default warn=6, block=7); the gated roles live in `REST_RULE_JOB_ROLES` in the same package.

**Worker profile + edit (built):** the worker-name cell on the grid (and the worker name in the **Do Not Book**, **Leavers**, and **Submissions** list pages) is a click target opening `WorkerProfileDialog` (`components/grid/dialogs/WorkerProfileDialog.tsx`). The dialog has a view mode and an **Edit** mode (react-hook-form + zod) to update full name, phone, job role (fixed-8 Select), and — only in grid/sheet context (when `sheetId` is passed) — the per-sheet standing note. Worker type is NOT an editable field; it is shown read-only and derived from the job role (see Job roles + worker type). Saves via `PATCH /workers/{id}` (`updateWorker`, `routes/workers.ts`) which updates the existing `workers` row in one txn (and `worker_sheets.notes` when `sheetId` given) — NO duplicate worker, NO schema change. `GET /workers/{id}` (`getWorker`) loads the detail. **start_date is NOT editable** — it is auto-derived from the first booking (see Leaver tracking) and shown read-only; the PATCH never accepts it. **Worker-type consistency is automatic:** `worker_type` is re-derived from `job_role` on every PATCH, and the rest-day rule + HGV-only event checks read `workers.job_role` live, so changing the role immediately governs both — e.g. switching a worker to Forklift makes a later CPC/Test event log return 400. **Events are now reached FROM the profile** (an "Events & history" button) rather than by clicking the name directly. **Route ordering:** `GET`/`PATCH /workers/:id` are registered AFTER the literal `/workers/do-not-book` routes so the literal paths are not shadowed. List-page edits invalidate that page's list query via the dialog's `onSaved`.

**Worker event logging (built):** from the grid, the worker's Events dialog (reached via the profile dialog's "Events & history" button) lets you log an event (type + date defaulting to today + optional notes), view that worker's events (most-recent-first list), and delete one. Event types: No Show (`no_show`), CPC Failure (`cpc_failure`), Test Failure (`test_failure`). Hard rule enforced server-side in `routes/events.ts`: CPC/Test failures may ONLY be logged for HGV workers; Warehouse workers get only No Show. The frontend filters the type options by worker type as UX, but the server is the source of truth (returns 400 if violated). The logged event's `sheetId` is the currently selected sheet; the list shows all of a worker's events regardless of sheet.

**Do Not Book flag + No Show (built):** workers carry a `doNotBook` boolean (column added to the workers table — see preferences note on the schema deviation). Flagged workers are filtered out of the bookable grid (`grid.ts` adds `doNotBook = false` to the WHERE) and surface only in a dedicated **Do Not Book** view (`pages/DoNotBook.tsx`, nav link in Shell) listing each flagged worker with their total no-show count and an "Allow booking again" button (reversible un-flag via `PATCH /workers/{id}/do-not-book`). The booking cell's status dropdown has a red **No Show** option (sentinel value, not a booking status) that logs a `no_show` event for that date via `POST /events` — a single no-show does NOT remove the worker. Backstop in `routes/events.ts`: once a worker accumulates 5 total `no_show` events, `doNotBook` is auto-set to true (only crosses the line once, still manually reversible); the create response carries `autoFlagged` so the UI can explain the removal. CPC/Test failure logging is unchanged (HGV only). The worker-name cell opens the worker profile dialog; the Events dialog is reached from there via "Events & history". **Display:** a date with a logged `no_show` event renders that grid cell with a red background and white "No Show" text (overriding any booking appearance), so it is immediately obvious; this is read from events data (the grid response includes a `noShows` array of `{workerId, shiftDate}` for the visible window) so it persists after refresh. A red "No Show" entry is in the grid colour key. **A no-show never outlives its cell:** clearing or changing a cell always removes the underlying `no_show` event(s) for that worker+date, so a cell never shows both a no-show and a status. This is enforced server-side via `clearNoShowsForDate` (`lib/noShow.ts`) called inside the same transaction from `bookings.ts` (PUT, both branches, and DELETE); a no-show-only cell (no booking row) is cleared from the grid via `DELETE /workers/{workerId}/no-shows/{shiftDate}` (`routes/events.ts`). **Auto-flag reversal:** removing a no-show reverses the Do Not Book flag ONLY when it crosses the worker's total no-show count from ≥5 back down to <5 (mirroring the auto-flag, which only fires crossing up while not already flagged) — a worker flagged while still below 5 was therefore flagged manually and is never auto-un-flagged. The same reconciliation runs when a `no_show` is deleted directly from the Events dialog (`DELETE /events/{id}`). The 5-no-show threshold lives in ONE place: `NO_SHOW_AUTO_FLAG_THRESHOLD` in `lib/noShow.ts` (imported by the auto-flag-on logic in `routes/events.ts`).

**Leaver tracking (built):** workers carry a `startDate` (date col) and a `status` ('active'/'left'). `startDate` = the worker's first-ever booking date, set automatically on the booking write paths (`bookings.ts` PUT and `grid.ts` CSV import). It only ever moves EARLIER — a genuinely earlier booking (out-of-order entry or import) corrects it; later bookings and deletes never move it forward. A worker with no bookings has `startDate = null` → length of service renders as "Not started" (never zero/error). Mark-as-leaver: a destructive **Mark as Leaver** button on the FRONT of `WorkerProfileDialog` (view mode, shown only when `worker.status === "active"`) opens `MarkLeaverDialog` as a stacked sibling (NOT closing the profile — callers conditionally mount the profile, so closing it would unmount the leaver dialog mid-flow). The dialog is a two-step **double confirmation**: step 1 explains the action and requires typing **DELETE** exactly (no trim — `confirmText === "DELETE"`; Continue stays disabled otherwise); step 2 records leave date (defaulting to today), a reason from the EXACT dropdown, and optional notes → `POST /workers/{id}/leave` inserts a `leavers` row and sets `status='left'` in one txn. **Idempotency:** the endpoint rejects a worker already `status='left'` (returns 409, no duplicate `leavers` row); the frontend also invalidates the worker query on success so the destructive button disappears once status flips. The same `MarkLeaverDialog` is still reachable from the Events dialog (unchanged wiring), so both entry points share the DELETE safeguard. Reasons live in ONE place — the `LeaverReason` enum in the OpenAPI spec (`low_rates`, `travel_distance`, `permanent_employment`, `shift_pattern`, `performance_issues`, `attendance_issues`, `other`); the same set is a CHECK constraint on `leavers.reason` (DB is the source of truth) and a human-label map (`LEAVER_REASON_LABELS`) in `pages/Leavers.tsx`. Marked leavers drop off the bookable grid (`grid.ts` WHERE adds `status='active'`) and surface only in a dedicated **Leavers** view (`pages/Leavers.tsx`, nav link in Shell) listing each leaver with leave date, reason label, and length of service (`startDate`→`leaveDate` whole days via `GET /leavers`' computed `serviceDays`; "Not started" when null). Reversible **Restore** (`POST /workers/{id}/restore`) deletes that worker's leaver rows and sets `status='active'`, returning them to the grid — restore is treated as a mistake-reversal (the `leavers` table is not retention history).

**Submission tracking (built):** records a worker being put forward to a client and its outcome (feeds reporting later). Uses the existing `submissions` table unchanged (links worker, optional `requirement_id`, optional `sheet_id`, `submitted_date`, `outcome`). Record from the **Submissions** view (`pages/Submissions.tsx`, nav link in Shell) via `RecordSubmissionDialog`: pick an active worker, date submitted (defaults today), optionally a sheet and — scoped to that sheet — a shift requirement, and a starting outcome. Outcomes live in ONE place — the `SubmissionOutcome` enum in the OpenAPI spec (`submitted`, `passed`, `rejected`), mirrored by a CHECK constraint on `submissions.outcome` (DB is the source of truth) and a label map (`SUBMISSION_OUTCOME_LABELS`) in `pages/Submissions.tsx`. Outcome is settable on create AND changeable later inline in the table (`PATCH /submissions/{id}`). The view filters by sheet and submitted-date range (`from`/`to`); where a submission is linked to a requirement it shows submitted-count vs the requirement's `quantity_needed` (the count is a SQL scalar subquery over ALL submissions for that `requirement_id`, independent of the active filters). **Requirement→sheet invariant:** a submission linked to a requirement always takes that requirement's sheet — `POST /submissions` overrides any client-supplied `sheetId` to the requirement's sheet so a submission can never claim one sheet while its requirement belongs to another. Shift requirements themselves are NOT managed in-app (no roster CRUD); they are exposed read-only (`GET /requirements`, `routes/requirements.ts`) purely so submissions can link to an existing client need. Two demo requirements are seeded on sheet 1 so the submitted-vs-needed display is demonstrable.

**Requirement coverage on the grid (built):** the main booking grid shows three summary rows at the bottom, directly under "Total Working Shifts" and aligned to the same date columns: **Required** (per day, sum of all `shift_requirements.quantity_needed` for the selected sheet on that date across all roles), **Filled** (workers booked that day with status Confirmed or Pre-Booked), and **Still Needed** (`max(0, Required − Filled)`). Days with no requirement render a neutral "-". The Required totals come from a per-day `requirements` aggregate on the `GET /grid` response (`grid.ts` groups `shift_requirements` by `req_date`, scoped to the sheet + visible window); Filled/Still Needed are computed client-side in `BookingGrid.tsx`. The rows respect the current Day/Week/Month view and selected sheet exactly like the rest of the grid (same `start`/`end`/`sheetId`).

The **Required** row is editable inline: each cell is a number input; on blur/Enter it saves via `PUT /requirements/daily` ({sheetId, shiftDate, required}) → `routes/requirements.ts`, then the grid refetches (Escape cancels, empty/0 clears the day). Because per-role roster CRUD is deliberately NOT in-app, the endpoint maintains ONE canonical `shift_requirements` row per sheet+date so the grid SUM always equals the entered total: it updates the first existing row and **zeroes** (never deletes) any extras to preserve submission FKs; inserts when none exists and `required > 0`. **Concurrency:** a transaction-scoped `pg_advisory_xact_lock(sheetId, hashtext(date))` serializes simultaneous edits of the same sheet+date so two first-writes on an empty day can't both insert and double the total. `required` is floored server-side (`Math.trunc`) since the spec's Zod only guarantees `number >= 0`.

The **Still Needed** cell is colour-coded as a traffic light by fill status (computed client-side): neutral when nothing is required, **red** when nothing is booked, **amber** when partially filled, **green** when fully filled (`filled >= required`). The colour key explains all three. This feature reads/writes only existing `shift_requirements` data — no table-structure changes.

**KPI Reports — operational metrics (built, first half):** a **Reports** view (`pages/Reports.tsx`, nav link in Shell, route `/reports`) backed by `GET /reports/operational` (`routes/reports.ts`, operationId `getOperationalMetrics`). Page-level filters apply to EVERY metric: (1) date range — **weekly** (Sun–Sat, prev/next + "This week"), **monthly** (1st–last, prev/next + "This month"), **custom** (from/to) — all resolve to `start`/`end`; (2) **depot/client** multi-select tickboxes (distinct `clientCompany`+`depot` combos from sheets, default all) → passed as comma-separated `sheetIds`; (3) **worker type** All/HGV/Warehouse (omit param = All). Metrics: **Active workers** (`status='active'` matching filters), **Requirements received** (Σ `shift_requirements.quantity_needed` in range), **Filled** (bookings Confirmed/Pre-Booked in range), **Fill rate %** (`filled/requirements`, null→"—" when no requirements), **No-shows** (`no_show` events in range). **Two-set scoping (server):** `depotClientSheetIds` = the ticked sheets regardless of type, used for the Active-workers `workerSheets` link; `scopedSheetIds` = those also matching the worker-type filter, used for requirements/filled/no-shows so the fill-rate numerator and denominator stay over the same sheet set. Active workers: all-selected → every active worker of the type; subset → only those linked via `workerSheets` to the selected sheets. Reads only existing data — no schema/table changes.

**KPI Reports — people metrics (built, second half):** added to the SAME Reports page below the operational cards, reusing the existing filter state exactly (date range, depot/client tickboxes, worker type) — the filters are not rebuilt. Backed by `GET /reports/people` (`routes/reports.ts`, operationId `getPeopleMetrics`), identical query params to `/reports/operational`. Metrics: **Submitted** (submissions in range by `submitted_date`), **Passed** (outcome `passed` in range), **Pass rate %** (`passed/submitted`, null→"—" when no submissions), **Leavers** (leavers in range by `leave_date`), **Leaver reasons** breakdown (count grouped by each of the 7 `LeaverReason` values, all reasons always shown incl. zeros, sums to the Leavers total), **Retention by length of service** (buckets under 1 week / 1–4 weeks / 1–3 months / 3–6 months / 6 months+), **CPC failures** and **Test failures** (event counts in range). **Worker-centric scoping (server):** unlike the operational half's two sheet-sets, people metrics resolve ONE `eligibleWorkerIds` set = workers whose own `worker_type` matches the filter AND (when a depot/client subset is ticked) are linked via `workerSheets` to a selected sheet; every metric is scoped via `inArray(workerId, eligibleWorkerIds)` (an `IN (subquery)`, NOT a join, so a worker linked to multiple selected sheets is never double-counted). **Retention is a current SNAPSHOT, not date-range bound:** every eligible worker with a `start_date` is bucketed by service length (`start_date`→`leave_date` for leavers via `max(leave_date)`, `start_date`→today for active); workers with no `start_date` are excluded from buckets and surfaced separately as **Not started**. Bucket day-thresholds are contiguous (`<7 / <28 / <90 / <180 / 180+`) so everyone with a start date lands in exactly one. **CPC/Test are HGV-only:** those events can only be logged against HGV workers (enforced at creation in `routes/events.ts`), so a Warehouse worker-type filter naturally yields zero. An empty eligible set short-circuits to an all-zero but fully-structured response (all 7 reasons, all 5 buckets present). Reads only existing data — no schema/table changes. A small set of demo leavers + CPC/test events is seeded so the breakdowns are demonstrable.

**Drag-fill batch booking (built):** the grid supports click-and-drag to fill a rectangle of cells (workers × dates) in one action. Mouse-down on a booking cell + drag + release; while dragging the selected rectangle shows a primary-colour inset ring (`select-none` on the table prevents text selection). A single-cell "drag" (no movement) opens that cell's normal editor popover unchanged; two or more cells open `BatchFillDialog` (status picker — Available/Pre-Booked/Confirmed/Rest/Off/Holiday; the **No Show** sentinel is deliberately excluded as it is not a real status — plus a 24h start time for working statuses). Apply writes EVERY selected cell exactly like a single edit (same statuses/colours/time, real `bookings` row, audit log) via `PUT /bookings/batch` (operationId `upsertBookingsBatch`, `routes/bookings.ts`). **Shared write path:** the per-cell upsert (insert/update + audit + earliest-`start_date` back-fill + no-show clearing) lives in ONE place — `applyBookingTx` (`lib/applyBooking.ts`) — used by BOTH the single PUT and the batch, so a batched cell can never diverge from a single edit. The whole batch runs in ONE transaction (all-or-nothing on unexpected error). **Rest rule is enforced PER-CELL, never bypassed:** `evaluateRestBatchForWorker` (`lib/restCheck.ts`) groups the selection by worker and classifies each date in ascending order with in-memory accumulation using the SAME `@workspace/rest-rules` primitives as single-cell — warn (6) cells count toward later runs, **blocked (7) cells are NOT written so they break the streak** (a later date after a blocked gap legitimately resets to 1, exactly mirroring single-cell semantics). First pass applies ok cells immediately, holds back warn cells, and reports blocked cells (toast: "N cells updated · M blocked (HGV 7-day rest limit)"). If any cell warns, an AlertDialog asks to "Book anyway"; confirming resubmits **only the warned cells** with `acknowledgeRestWarning: true` — the already-applied ok cells are NOT re-sent, so their rows (and `updated_at`) are never rewritten and concurrent edits between the two passes are not clobbered (the classifier is ack-independent, so re-evaluating just the warned dates against the now-persisted ok cells yields identical decisions). Do Not Book / leaver workers are already filtered off the grid, so they are never in a selection.

**Booking-cell note (built):** each booking carries an optional free-text `note` (nullable `note TEXT` column on `bookings`, mirrored in `attached_assets/extracted_files/schema.sql`) — an ADDITION alongside status + start time, never a replacement. A cell can have status only / status+time / status+note / status+time+note. The cell editor popover (single-cell) and `BatchFillDialog` (drag-fill) both show an always-optional Note textarea (hidden only for the No Show sentinel, which is not a booking). Blank/whitespace notes save as `null` (`.trim() || null`). The grid renders a small 📝 indicator (bottom-left of the cell) with the full note in its `title`/`aria-label` for hover; no-show cells never show it. Note is threaded through the SHARED write path `applyBookingTx` (`lib/applyBooking.ts`) so single PUT and batch are identical, and serialized back via `serializeBooking`; `GET /grid` returns it so it persists across reloads. Note is in the Booking, BookingInput, and BatchBookingInput OpenAPI schemas. Deliberately unchanged: audit log / `describeBooking` (notes are not audited), CSV import (note defaults null).

**Admin-only destructive deletes (built):** two destructive actions are admin-only — server-enforced via per-route `requireAdmin` AND hidden in the UI for standard users (gated on `useGetCurrentUser().role === 'admin'`). (1) **Delete a whole sheet** (`DELETE /sheets/{sheetId}`, operationId `deleteSheet`, `routes/sheets.ts`): `bookings.sheet_id` is `ON DELETE RESTRICT`, so the handler deletes the sheet's bookings inside the same txn before deleting the sheet; everything else is automatic (`sheet_contacts`/`worker_sheets`/`shift_requirements` cascade; `submissions.sheet_id`, `events.sheet_id`, `submissions.requirement_id`, `audit_log.booking_id` set null). UI lives in `SheetSettingsDialog` (Danger Zone + confirm), with an `onSheetDeleted` callback threaded through `GridToolbar` → `Grid.tsx` (clears the selected sheet). (2) **Delete a leaver record** (`DELETE /leavers/{workerId}`, operationId `deleteLeaverRecord`, `routes/leavers.ts`): deletes the worker's leaver row(s) but leaves `status='left'` — this is DISTINCT from **Restore** (which deletes leaver rows AND reactivates to `status='active'`). A worker deleted this way appears on neither the grid nor the Leavers list (intended "purge from leaver tracking"); worker/booking/event history is preserved. UI is an admin-only per-row Delete button + confirm in `pages/Leavers.tsx`.

Deliberately NOT built: shift-requirements roster CRUD.

## Gotchas

- `connect-pg-simple`'s `createTableIfMissing` does NOT work under the esbuild bundle (it reads `table.sql` relative to the package, which isn't bundled). The `session` table must be created manually in the DB; do not rely on auto-create.
